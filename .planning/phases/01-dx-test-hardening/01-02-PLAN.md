Revision note (01-REVIEWS.md consensus finding #1, HIGH/Codex + MEDIUM/OpenCode): the original event-order-only design for the two "destroy waits" tests could still pass under a genuine regression, because `["run-returned", "destroy-released"]` is also what you'd observe if the destroy goroutine simply hadn't been scheduled yet before `allowRunReturn` was closed. This revision adds a `TryLock()`-based contention probe — performed by the main test goroutine on the exact mutex Destroy()/Tensor.Destroy() must acquire, immediately after `<-runStarted` and before spawning the destroy goroutine — that deterministically proves the lock is already held by the in-flight Run(), independent of any goroutine's scheduling. This is a stronger, non-probabilistic proof than a mock-side rendezvous signal would be, and requires no production code changes (test-file-only, same as before).

**New pattern this revision introduces — deterministic lock-contention probe (addresses 01-REVIEWS.md consensus finding #1):**

From `ort/session.go` (`AdvancedSession.Run`/`Destroy`, lock ordering documented at lines ~19-233): `Run()` calls `s.runMu.Lock()` (a plain `sync.Mutex`) BEFORE invoking the mock `runSessionFunc`, and holds it until `Run()` returns. `Destroy()` also calls `s.runMu.Lock()`. Since `<-runStarted` only unblocks after `runSessionFunc` has been entered, `session.runMu` is *guaranteed* to already be locked by `Run()` at that point — so a `TryLock()` probe on `session.runMu` performed by the main test goroutine right after `<-runStarted` is a synchronous, deterministic way to confirm the lock is genuinely contended, with zero dependency on when any other goroutine gets scheduled:
```go
if session.runMu.TryLock() {
	session.runMu.Unlock()
	t.Fatalf("expected session.runMu to be held by the in-flight Run(), TryLock unexpectedly succeeded")
}
```

From `ort/tensor.go` (`Tensor[T].Destroy` line ~169, `Tensor[T].lockForRun` line ~215): `Tensor[T].runMu` is a `sync.RWMutex`. `Run()`'s value-locking path calls `inputTensor.lockForRun()`, which takes `inputTensor.runMu.RLock()` for the duration of the mock call (held until `Run()` releases it). `Tensor[T].Destroy()` calls `inputTensor.runMu.Lock()` (a write lock), which cannot be acquired while any RLock is held. The equivalent probe:
```go
if inputTensor.runMu.TryLock() {
	inputTensor.runMu.Unlock()
	t.Fatalf("expected inputTensor.runMu to be held (RLock) by the in-flight Run(), TryLock unexpectedly succeeded")
}
```
Both `sync.Mutex.TryLock()` and `sync.RWMutex.TryLock()` are stdlib (Go 1.18+); the repo already requires a newer Go version (`go.mod` pins `go 1.25.0`). `ort/session_test.go` is package `ort` (not `ort_test`), so it has direct access to these unexported fields.
