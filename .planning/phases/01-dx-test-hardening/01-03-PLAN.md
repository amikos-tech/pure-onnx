<rationale>
## Resolving the phase's open question: -short wiring IS in scope (revised per 01-REVIEWS.md)

CONTEXT.md D-06 requires stress tests "gated behind testing.Short(), so normal go test ./... / CI runs skip them by default." D-08 enumerates CI/TESTING.md changes explicitly but is silent on Makefile's test/precommit/test-race targets and the two existing CI unit-test steps. RESEARCH.md's Common Pitfall #2, Open Question #1, and PATTERNS.md's "Open Question for Planner" all flag that without adding -short somewhere, testing.Short() gates nothing -- grepping the repo confirms zero existing -short usage in Makefile or ci.yml.

01-REVIEWS.md's cross-AI review (Codex + OpenCode, both HIGH) caught two things the original version of this plan got wrong:

1. A bare `go test ./...` typed directly by a contributor, with no flags, will NEVER pick up `-short` no matter what Makefile/CI do -- `testing.Short()` is only true when `-short` is explicitly passed on that exact invocation. The literal claim "go test ./... skips stress tests by default" is false and must not appear in this plan's success criteria or TESTING.md wording. This plan now states precisely which *repository-provided* commands (`make test`, `make precommit`, `make test-race`, CI's `test` job) skip the stress tests, and calls out explicitly that a raw `go test ./...` invocation does not.

2. `make test-race` (`Makefile`, `$(GO) test -v -race ./ort/...`) has no `-run` filter and no `-short`, so -- contrary to the original plan's assumption that it "targets its own curated `-race` subset, never runs `TestStress*`" -- it WILL run all new `TestStress*` tests unless changed.

Decision (revised): `-short` is added to Makefile's `test:` target, `precommit`'s `go test ./...` step, `make test-race`'s target, AND both CI `test` job steps (Unix + Windows) in ci.yml. Adding `-short` to `test-race` (rather than switching it to a curated `-run` regex) is the more consistent fix: it mirrors the exact pattern already used for `test`/`precommit` in this same plan, requires a one-line change, and preserves `test-race`'s existing behavior of running the full `./ort/...` package under `-race` (minus the now-skipped stress tests) rather than introducing a hand-maintained allowlist that would need updating every time a new non-stress race test is added. The existing `test-race-ort-concurrency` CI job is left unchanged -- its curated `-run` regex is a fixed list of specific test names that never matches `TestStress*`, so it doesn't need `-short` to avoid running the new tests (only `make test-race`, which has no `-run` filter at all, needed the fix).
</rationale>

```go
func TestConcurrentInitialization(t *testing.T) {
	resetEnvironmentState()
	if err := SetSharedLibraryPath("/nonexistent/path.so"); err != nil {
		t.Fatalf("unexpected error setting library path: %v", err)
	}
	var wg sync.WaitGroup
	concurrency := 10
	mu.Lock()
	refCount = 1
	mu.Unlock()
	for i := 0; i < concurrency; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			_ = InitializeEnvironment()
		}()
	}
	wg.Wait()
	mu.Lock()
	expectedCount := 1 + concurrency
	if refCount != expectedCount {
		t.Errorf("expected refCount to be %d after concurrent inits, got %d", expectedCount, refCount)
	}
	mu.Unlock()
	resetEnvironmentState()
}
```

From ort/environment.go (package-level state and the exact fast-path logic these tests depend on, lines ~22-51 and ~90-138, ~200-245): `InitializeEnvironment()` is `if refCount > 0 { refCount++; return nil }` -- i.e. it ONLY attempts the real (failing, against a nonexistent path) `loadLibrary` call when `refCount == 0`. `DestroyEnvironment()` is `if refCount == 0 { return nil }; refCount--; if refCount > 0 { return nil }` -- decrementing only, with real teardown logic gated behind `refCount` reaching 0 (and further gated behind `ortAPI != nil`/`ortLib != 0`, both of which stay nil/0 throughout these tests since the real loader is never reached). This is exactly why 01-REVIEWS.md's consensus finding #3 is correct: starting from `refCount == 0` makes every `InitializeEnvironment()` call attempt and fail the real load, and every paired `DestroyEnvironment()` a no-op -- seeding `refCount = 1` before spawning workers is what makes every call take the fast increment/decrement-only path instead.
```go
func InitializeEnvironment() (err error) {
	ortCallMu.Lock()
	defer ortCallMu.Unlock()
	mu.Lock()
	defer mu.Unlock()
	if refCount > 0 {
		refCount++
		return nil
	}
	// ... real loadLibrary path, only reached when refCount == 0 ...
}

func DestroyEnvironment() error {
	ortCallMu.Lock()
	defer ortCallMu.Unlock()
	mu.Lock()
	defer mu.Unlock()
	if refCount == 0 {
		return nil
	}
	refCount--
	if refCount > 0 {
		return nil
	}
	// ... real teardown path, only reached when refCount just hit 0;
	// ortAPI/ortLib stay nil/0 throughout these tests, so this path is a safe no-op ...
}

func IsInitialized() bool { mu.Lock(); defer mu.Unlock(); return refCount > 0 }
func GetVersionString() string { /* returns "0.0.0-dev" if refCount == 0 || getVersionStringFunc == nil; otherwise calls the (nil, in these tests never-loaded) function pointer -- safe as long as refCount never drops to 0 mid-test */ }
func SetLogLevel(level LoggingLevel) error { /* returns an error whenever refCount > 0 -- "cannot change log level after environment is initialized"; no refCount side effect either way */ }
```
